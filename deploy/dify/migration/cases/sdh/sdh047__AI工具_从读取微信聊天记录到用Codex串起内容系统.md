**很多人缺的并不是一个又一个 AI 工具，而是一条能长期工作的路**：

今天收藏的东西，明天还能找到；找到以后，能够变成自己的观点；写公众号、做短视频、发朋友圈、做方案时，它还能再次被调用。

我自己原来的状态也很典型：客户问题在微信，文章收藏在手机，网页在浏览器，长文在飞书，零散笔记在不同文件夹。每个平台里都有东西，但真正要写内容时，我还是会从头想。

所以我开始搭这套系统，不是为了把工具都装一遍，而是想解决三个很朴素的问题：

1. 好内容能不能用最短的路径先收下来？
2. 收下来的东西能不能被加工，而不是躺在收藏夹里？
3. 加工后的知识能不能顺利进入我真正发布和交付的地方？

## 二、一句话讲清楚：IMA 收，Obsidian 炼，飞书享，Codex 调

![图 2｜IMA、Obsidian、飞书与 Codex 的总流程图](https://feishu.cn/file/CATabJ3dQoJyJAxSgGmc4EARnBD)

| **工具** | **只负责一件事** | **我什么时候用** |
|-|-|-|
| IMA | 收 | 手机上临时保存文章、网页，并基于已上传内容查询 |
| Obsidian | 炼 | 保存本地 Markdown，拆分观点、建立关联和沉淀主版本 |
| 飞书 | 享 | 需要排版、评论、协作、交付或给别人阅读时 |
| Codex | 调 | 读取、整理、拆分、写入、同步，并在目标端读回验收 |

我后来给四个工具定了很清楚的分工。

- IMA 负责“收”。它长在手机和微信使用场景里，适合临时看到内容时快速保存，也方便基于已上传内容做问答。
- Obsidian 负责“炼”。它本质上是电脑里的 Markdown 文件夹，适合长期保存、拆分、改写、做双链和沉淀自己的方法。
- 飞书负责“享”。需要排版、协作、评论、交付或给别人看时，我会把成品放到飞书。
- Codex 负责“调”。它连接这些入口和仓库，替我完成读取、整理、拆分、写入、同步和验收。

如果只记一张图，可以记下面这一条：

手机文章、微信记录、电脑网页、自己写过的文档  
→ IMA 或 Obsidian Inbox  
→ Codex 读取和拆分  
→ Obsidian Notes / Archive  
→ IMA、飞书  
→ 公众号、短视频、朋友圈、课程或方案

这四个工具不是缺一不可。第一次搭建时，甚至不需要全部安装。你只要先有一个入口、一个加工仓和一个出口，就能开始。

## 三、我没有先做“大系统”，而是先跑通一条内容

![图 3｜IMA 接入 Codex 后可调用的读取与写入能力](https://feishu.cn/file/EPhRbK0pNodzVmxg7iMcRH5ZnIh)

![图 4｜文件上传与目标端读回：五道验收检查](https://feishu.cn/file/ML4nbj4RXoWlPgxTMwZc44Pmnqh)

这是我现在最想提醒新手的一点：**先手动跑通一条，再谈自动化。**

第一次测试时，我只选一篇文章。完整过程是：

1. 在手机上把文章分享到 IMA。
2. 回到 IMA，确认能打开全文。
3. 让 Codex 读取这篇内容，保存到 Obsidian。
4. 在 Obsidian 里检查标题、正文开头和结尾、来源链接、图片或附件说明。
5. 让 Codex 从原文里拆出一条可以独立使用的观点。
6. 用这条观点写一条朋友圈，或者写成一个短视频开头。
7. 把成品放到飞书，再从飞书打开检查一遍。

走完这七步，我才认为这条工作流“通了”。

以前我很容易把“接口返回成功”当成完成。后来发现，创建成功可能只是生成了一篇云文档，文档不一定进了目标知识库；同步成功也可能只同步了一个需要登录的空链接；文件出现在 Obsidian 里，也可能正文少了一半。

所以现在我的验收标准很笨，但很有效：**到目标端重新搜索、打开、从头读到尾**。**写进去是一回事，目标端能找到、能打开、内容完整，是另一回事**。

不要追求全自动化！

### 1. 手机上的内容：先进入 IMA

【视频演示】手机浏览器里的内容如何保存到 IMA（25 秒）

手机场景最重要的是快！

看到一篇文章，如果想着“等回到电脑再整理”，大概率就没有以后了。

我的做法是点击分享，选择 IMA，放进固定知识库，比如这个知识库就叫“待整理”。

保存以后在 IMA 打开一下，能打开，才算收下。

IMA 只是第一站，我会手动（如果恰好手机和电脑在一起协同）或者用 Codex 批量拉到 Obsidian，原始内容和加工结果分开存。

### 2. 电脑网页和公众号文章：按完整度选工具

![图 5｜浏览器里的 IMA、Obsidian Web Clipper 与飞书剪存入口](https://feishu.cn/file/YMYsb4IwyoxsCLxS7sacwiKZn9d)

普通网页我之前会先用 [Obsidian Web Clipper](https://obsidian.md/help/web-clipper)。它是 Obsidian 官方的浏览器扩展，可以把网页内容保存到本地 Vault。

但“生成了 Markdown 文件”不等于保存完整。网页里的懒加载图片、复杂表格、轮播内容都有可能丢。我会先把页面慢慢滚到底，再剪藏，然后检查正文开头、结尾、图片和原链接。但有的时候还是会丢，抓取内容不完整！

公众号长文或复杂图文，如果 Web Clipper 保存不完整，我就直接删掉，然后我会改用飞书剪存做一遍，看下效果。

飞书更适合保留排版和后续协作。

选择标准不是哪个工具更高级，而是哪一个能把这篇内容完整保存下来，处理之前也要确保完整性。

所以当我大批量长期使用这几个插件后，我发现Ima存的更好，因为Ima是存的链接而不是剪藏，所以不会丢内容。

如果要长期监控固定公众号的更新，我才会上自动化：WeRSS 提供稳定来源，本地脚本负责检查和去重，飞书负责提醒和表格记录，Obsidian 保存正文，同时保留日志和授权失效提醒。刚开始不要监控几十个号，先用一到三个账号做测试。

### 3. 以前的微信聊天记录：直接读本地 Vault

这个相信是很多人的最爱和刚需！

【视频演示】在手机微信发出指令，Hermes 调用本机 Vault，再由 Codex 整理结果。

电脑端读取微信 Mac 4.x 历史数据，我使用的是 [yichen-wechat-local-vault](https://github.com/mcncarl/yichen-skills/tree/main/yichen-wechat-local-vault)。

它负责维护本机已经解密的 Vault，Codex 再基于明确的群聊、联系人、关键词和时间范围去查询。

相比旧版 wechat-cli，它还可以读取语音、朋友圈；不需要降低微信版本，也不用安装重签名版微信。

电脑端的链路很简单：

微信本地数据 → yichen-wechat-local-vault → Codex → Obsidian 或飞书

只有当我想在手机微信里远程下指令时，才在前面加 Hermes：

手机微信指令 → Hermes → 同一个本地 Vault → Codex → 返回结果

Hermes 是消息入口和调度层，不是历史数据库。

Codex 是理解和执行的大脑，也不会凭空拥有微信记录。把这三层分清以后，排错会容易很多。

### 2. 正确的安装顺序：先基础链路，再加入口

1. **先装 Codex 和 Obsidian。**让 Codex 能看到一个明确的 Vault 路径，先写入并读回一篇测试笔记。
2. **再选一个内容入口。**手机内容选 IMA，电脑网页Web Clipper+ima+飞书剪存都装上，同时存感受对比。
3. **需要电脑微信历史数据时安装一尘 Skill。**先验证本地 Vault，再做限定范围查询。
4. **需要手机微信远程指挥时才加 Hermes。**先让 Hermes 完成普通对话和 PONG，再调用一尘 Skill。

### 3. 第一步：让 Codex 连接 Obsidian

Codex 不是必须要通过Obsidian  MCP 才能读 Obsidian。

Vault 本质上就是本机文件夹。先在 Codex 里把这个文件夹添加为工作目录，再复制下面的提示词：

```text
这是我的 Obsidian Vault 路径：【粘贴绝对路径】。

请先只读检查这个路径是否正确，不要扫描其他目录。
确认无误后：
1. 保留现有结构，不覆盖已有文件；
2. 如果缺少，就创建 Inbox、Notes、Archive、Outputs 四个文件夹；
3. 在 Inbox 新建一篇“工作流验收测试”Markdown；
4. 写入标题、创建时间、来源和一句测试正文；
5. 重新读取这个文件，告诉我标题、路径、正文开头和结尾；
6. 不安装 Obsidian MCP，不删除、移动或批量改写任何旧笔记。

只有“写入后重新读取完整”才算成功。
```

验收时要看到：文件出现在正确 Vault、Obsidian 能打开、Codex 读回的标题和正文一致。详细安装说明可看：[《如何创建 Obsidian：从安装到第一个知识库》](https://my.feishu.cn/wiki/KJsbwbyPDi39xgkSSaGc2wFwn7b)。

### 4. 手机内容进入 IMA，再让 Codex 读取

先到 [IMA Agent Interface](https://ima.qq.com/agent-interface) 手动申请 Client ID 和 API Key。

然后把下面的提示词发给 Codex：

```text
请安装并检查最新版 ima-skill，先确认 Node.js 版本满足要求。

我会在本机按你的提示输入 IMA Client ID 和 API Key。
请把凭证安全保存在本机私有配置目录：
- 目录权限 700；
- 凭证文件权限 600；
- 不在输出、日志、截图或 Git 中显示密钥。

配置后调用 IMA OpenAPI 的 list_note，做一次 limit=1 的只读鉴权验证。
然后列出我能访问的 IMA 知识库名称，不做任何写入。

最后告诉我：
1. Skill 是否安装成功；
2. 鉴权是否成功；
3. 能否列出知识库；
4. 如果失败，失败发生在哪一步。
```

能列出知识库以后，再测试一篇真实内容：

```text
请在 IMA 中按完整标题搜索【笔记标题】，只处理这一篇。

读取正文后：
1. 保存原文到 Obsidian 的 Inbox；
2. 保留原标题、来源链接、IMA 笔记 ID 和同步时间；
3. 检查正文开头、结尾、链接和图片说明；
4. 写入后重新读取 Obsidian 文件；
5. 告诉我 IMA 端命中数量、Obsidian 文件路径和读回结果。

不要批量同步，不覆盖同名文件；发现同名时先停下来告诉我。
```

完整版参考：[《IMA 知识库与 Codex 打通教程》](https://my.feishu.cn/wiki/RhmywZI0bidGSTkhvbecIrdPnlb)。

### 5. 把飞书接到 Codex

先在 [飞书开放平台](https://open.feishu.cn/) 创建企业自建应用，开通需要的云文档和知识库权限并发布。拿到 App ID 和 App Secret 后，不要把 Secret 写进下面这段公共提示词：

```text
请按 lark-cli 当前版本的内置 Skill 和 --help 完成飞书接入，不要照抄旧版命令。

1. 从官方仓库安装或更新 lark-cli；
2. 引导我在本机完成应用配置，不在输出中显示 App Secret 或 token；
3. 发起 docs、drive、wiki 范围的用户授权；
4. 注意 auth login 本身不加 --as user，后续读取和写入 API 时才使用 --as user；
5. 验证用户授权状态；
6. 只读列出我能访问的飞书知识库；
7. 读取一篇我指定的飞书文档；
8. 不创建、不移动、不删除任何内容。

最后告诉我：lark-cli 版本、用户身份是否有效、知识库列表是否可见、指定文档是否完整读回。

只读验收通过后，再单独测试写入：

要求：
1. 先检查目标知识库和节点是否唯一；
2. 创建前搜索同名文档，存在同名就停止；
3. 保留标题、正文层级、列表、表格和链接；
4. 创建后确认文档已移动到目标知识库，不要只停在云盘；
5. 回到知识库重新搜索并读取新文档；
6. 报告文档链接、目标节点和读回结果。

不要覆盖、删除或移动其他文档。
```

完整版参考：[《飞书知识库与 Codex 打通教程》](https://my.feishu.cn/wiki/MTJuwwd2kiMtxIkftcPcV5Qlnjb)。

### 6. 电脑端读取微信：安装一尘 Skill

这条路线只适用于 **macOS + 微信 Mac 4.x**。先确认这台电脑已经有你需要的本地微信记录。新电脑没有历史记录时，要先用微信官方迁移功能同步；Codex 和一尘 Skill 不能凭空找回电脑上不存在的数据。

**电脑端链路：**微信本地数据 → yichen-wechat-local-vault → Codex → Obsidian 或飞书。

```text
请在我的 Mac 上安装并验证 yichen-wechat-local-vault。

项目地址：
https://github.com/mcncarl/yichen-skills/tree/main/yichen-wechat-local-vault

目标：
1. 安装到 Codex Skills 目录，并使用 Skill 自己的隔离环境，不污染系统 Python；
2. 审计现有安装和 Vault 状态，已有组件直接复用；
3. 如果已有可用 Vault，先做只读 status；没有时再按 Skill 说明初始化；
4. 首次全量解密、需要 macOS 权限或需要我操作微信时，暂停并明确告诉我；
5. 完成后只读列出最近会话；
6. 让我指定一个联系人或群聊、关键词和时间范围，再读取少量记录验收；
7. 告诉我查询覆盖的时间范围、记录数和缺失项。

安全边界：
- 不发送、修改或删除任何微信消息；
- 不上传、移动或复制明文 Vault；
- 不输出 key、salt、token、wxid、数据库路径或整库原文；
- 不做无限范围导出；
- 不承诺零风险。
```

安装后，Codex 应先执行只读状态检查，再按需进行日常增量刷新。下面第一条命令只读检查状态，第二条命令会写入本地私密 Vault；如果实际路径不同，让 Codex 自动定位 Skill 目录：

```bash
~/.codex/skills/yichen-wechat-local-vault/.venv/bin/python \
~/.codex/skills/yichen-wechat-local-vault/scripts/vault_cli.py status --format text

~/.codex/skills/yichen-wechat-local-vault/.venv/bin/python \
~/.codex/skills/yichen-wechat-local-vault/scripts/decrypt_all_dbs.py --mode incremental
```

状态可用以后，再发一个范围明确的查询：

```text
请先增量刷新本地微信 Vault；这一操作会写入本地私密 Vault，但不会修改微信源数据库或发送消息。

找到【联系人或群名】最近【7 天】提到【关键词】的记录，最多【20 条】。
先确认目标会话唯一，再开始查询。

输出要求：
1. 先给结论；
2. 只引用必要短句；
3. 标注时间范围、命中数量和可能缺失项；
4. 不显示路径、wxid、密钥或完整聊天原文；
5. 不发送、修改或删除微信消息。
```

完整版参考：[《用 yichen-wechat-local-vault + Codex 读取微信数据》](https://my.feishu.cn/wiki/TN3XwqUiCiDahik0DHMcmtF2nOc)。

### 7. 手机微信远程下指令：再加 Hermes

**前置条件：**上一节的本地 Vault 必须已经能在电脑上查询。Hermes 只是微信里的消息入口和调度层，不负责解密历史数据库。

**手机端链路：**微信新指令 → Hermes → 同一个 yichen-wechat-local-vault → Codex → 微信回复。

```text
请在我的 Mac 上搭建并验收：
微信 → Hermes → yichen-wechat-local-vault → OpenAI Codex。

要求：
1. 复用现有组件，缺少时才安装；Hermes 使用官方安装方式；
2. 先验证 yichen-wechat-local-vault 的只读 status，为 Hermes 创建可正常调用的兼容层，不复制明文 Vault；
3. 通过 hermes model 选择当前账号可用的 OpenAI Codex 模型，并先完成一次普通对话；
4. 配置 Hermes 原生 Weixin：私聊仅限本人，群聊关闭，不允许所有用户访问；
5. 微信消息不得触发密钥提取、全量解密或无限范围导出；
6. 不得输出密钥、salt、wxid、数据库路径和整库原文；
7. 关闭工具进度和中间回复，只发送最终结果；
8. 依次验收：Skill status、网关在线、微信 PONG、终端重启网关、重启后再次 PONG、一次限定范围的历史查询。

任一步失败都不要说安装完成，请明确说明失败步骤。
需要我登录、扫码或批准系统权限时暂停，等我本人完成。
```

验收顺序不能倒：先运行 `hermes doctor`，再确认 `hermes gateway status`；微信发送“只回复 PONG”收到回复后，在电脑执行 `hermes gateway restart`，恢复后再次测试 PONG。两次都成功，最后才测试历史查询。

```text
请使用 yichen-wechat-local-vault，只读查询【联系人或群名】最近 7 天提到【关键词】的记录，最多 20 条。

先给结论，只引用必要短句，不显示路径、wxid、密钥或完整聊天原文。
如果本地 Vault 不是最新的，请告诉我需要在电脑端增量刷新，不要通过微信触发首次全量解密。
```

完整版参考：[《微信 + Hermes + Codex：在手机上查询本机微信记录》](https://my.feishu.cn/wiki/WwC7wwlZMiFIpfka4ydcg9EYnC1)。

### 8. 最后用一篇真实内容跑完整条链路

工具各自验收成功后，再用下面这段把“取料、入库、加工、分发”串起来。第一次只处理一篇，不开定时任务。

```text
请帮我手动跑通一条内容工作流，只处理一篇，不做定时任务。

来源：
- 平台：【IMA / 微信本地 Vault / 网页】
- 内容标题或对象：【填写】
- 时间范围或来源链接：【填写】

目标：
1. 把原始内容保存到 Obsidian 的 Inbox，保留来源、日期和源 ID；
2. 检查正文开头、结尾、链接、图片或附件说明；
3. 从原文拆出 3 条候选语料，每条只保留一个观点、案例或数据；
4. 由我确认后，只把选中的 1 条写入 Notes；
5. 基于这条笔记生成一个【朋友圈 / 短视频开头 / 公众号段落】草稿，保存到 Outputs；
6. 如需分享，再创建飞书云文档并放入【知识库名称 / 目标节点】；
7. 分别在源端、Obsidian 和飞书重新搜索、打开并读回。

安全和版本规则：
- 发现同名内容先停下来，不覆盖；
- 不删除、不批量移动、不自动发布；
- API 返回成功不等于完成；
- 最后给我一张验收表：来源、目标、路径或链接、读回结果、缺失项。
```

### 9. 怎样才算真的打通

| **检查点** | **必须看到的结果** | **不能当成成功的情况** |
|-|-|-|
| Obsidian | 目标文件在正确 Vault 和目录中，标题、正文首尾、来源都能读回。 | 只看到生成了一个文件名。 |
| IMA | 按标题重新搜索，能打开正文；关联知识库和目标位置正确。 | 只看到接口返回成功。 |
| 飞书 | 目标知识库里能搜到文档，打开后层级、列表、表格和链接完整。 | 只在云盘里创建了文档，没有进入知识库。 |
| 微信本地 Vault | 目标会话唯一，时间范围和命中数量明确，抽查结果能对应原记录。 | 拿旧快照或同名群聊的结果当最新答案。 |
| Hermes | 普通对话、第一次 PONG、重启后第二次 PONG、限定历史查询依次成功。 | 网关进程启动了，但微信里收不到回复。 |

## 五、内容进库以后，怎么避免变成电子仓库

| **目录 / 状态** | **里面放什么** | **下一步动作** |
|-|-|-|
| Inbox | 刚进入系统、还没判断的原料 | 删除、提炼或转入 Archive |
| Notes | 已经提炼、可以复用的观点、案例和数据 | 建立关联，等待真实调用 |
| Archive | 已经处理但暂时不用的原文 | 保留来源，不反复进入 Inbox |
| Outputs | 准备发布或交付的最终成品 | 发布、协作并记录最终版本 |

**收藏不是知识库。**收藏只是把“以后可能有用”换了一个地方堆着。

我在 Obsidian 里把内容至少分成四种状态：

- Inbox：刚进来的原料，还没判断。
- Notes：已经提炼过、以后可以复用的笔记。
- Archive：处理过但暂时不用的原文。
- Outputs：已经准备发布或交付的成品。

**真正决定知识库有没有用的，是 Inbox 能不能持续流向 Notes 和 Outputs**。

我的基本加工单位不是“一篇收藏”，而是一条语料块。**一条语料块只保留一个可以独立使用的观点、案例或数据**，同时写清楚来源、适用场景和自己的判断。

比如一篇文章里有八个观点，我不会把整篇原文直接当成自己的知识。

我会让 Codex 先拆出候选块，再由我确认哪些值得保留。最后留下来的可能只有三条：

- 一个能放进公众号正文的观点；
- 一个能讲给客户听的案例；
- 一组需要保留出处的数据。

清洗完成以后，我会立刻选一条去使用。它可以是一条朋友圈、一个短视频开头、公众号的一段正文，或者方案里的一页。只有当内容真的进入作品或工作，我才认为它完成了一次流转。

## 实战案例｜一篇 IMA 原文如何经过清洗、调用和成材

前面讲的是方法，这里补一段刚刚真实跑通的过程。它不是我事先画出来的流程图，而是一篇真实的 IMA 原文，经过 Codex 和 Obsidian 处理以后，最终变成公众号草稿和朋友圈文案的完整记录。

**这次真正验证的，不是“AI 能不能写文章”，而是原料能不能被清洗、按目标调用，并针对不同平台长成不同成品。**

一条文章生成「语料块」反向链接 关联内容工作流设计流程内容工作流实际测试

### 1. 原料：从 IMA 精确同步一篇真实文章

本次使用的原文是《8月 AI 一人公司实战营｜手把手教你搭建 Agent 内容获客系统，从流量到变现（陪跑 2 个月）》。Codex 通过 IMA API 在“石更新的知识库”中精确找到同名内容，再同步到 Obsidian。同步后重新读取目标文件，确认标题、元信息和正文完整。

到这里仍然只完成了取料和入库。文档虽然已经进入 Obsidian，但还不能直接支持写作。

### 2. 清洗：把一篇招生文章变成 15 个可追溯语料块

原文同时混合了观点、工具案例、课程安排、销售话术和作者自报成绩。如果只做摘要，它仍然是一篇缩短后的招生文章。真正的清洗，是先完整保存标准素材卡，再只拆出以后真的可能使用的内容。

| 类型 | 数量 | 保留内容 |
|-|-|-|
| 观点 | 6 | AI 产出与商业价值、工具能力与商业系统、Agent 工作流等 |
| 案例 | 4 | 信息日报、选题安排、录音转存和多平台内容管理 |
| 数据 | 2 | 仅保留能够明确说明当期产品交付设计的信息 |
| 金句 | 3 | 一人公司、商业系统和持续经营相关表达 |

每个语料块都双链回标准素材卡。原文中没有独立证据的收入、销量、学员数量和效果数字，没有被包装成可以直接传播的“可信数据”；需要保留的课程信息也增加了使用边界。

**所以，清洗不是把所有东西都留下，而是决定什么值得留下、它属于哪一类，以及它可以在什么边界内使用。**

### 3. 调用：先生成选题，再由人决定写什么

语料准备好以后，Codex 没有直接写正文，而是先读取账号定位卡、目标用户痛点库、发布目的清单，以及公众号和朋友圈的平台规则。

当系统发现账号定位卡和痛点库还是空模板时，没有假装已经完成个性化匹配，而是把这个限制明确标注出来。随后基于现有语料生成 5 个候选选题，每个选题都包含核心观点、支撑语料双链、适用用户和推荐理由。

我最终选择的是：《会用 AI 为什么还赚不到钱？问题不在工具，在商业系统》。

选题确认以后，案例、数据和金句才围绕同一个核心观点重新组合。与主题无关的课程价格、报名方式和成绩数字全部不用。

### 4. 成材：同一个选题，分别长成公众号和朋友圈

公众号版本负责把问题讲透：为什么 AI 生产能力增强，不等于自然获得流量和收入；从“我是谁”到“怎么持续做下去”，中间还缺哪些商业问题。文章末尾列出实际调用的 7 个语料块，方便随时回查。

朋友圈版本没有把公众号长文机械缩短，而是从刚刚发生的真实过程切入，只保留一个判断、一项支撑和一个提问。核心表达是：

> 会用 AI 写文章，不等于有内容获客能力；会用 AI 做产品，也不等于知道怎么定价、怎么卖。中间缺的不是工具，是商业系统。

这次之后，我对“成材”的理解也更清楚了：不是把 Markdown 复制到发布平台，而是根据平台、用户和发布目的，让同一组原料长成不同形态。

**完整实战复盘：**[《一次真实的五环实战：从 IMA 原文到公众号与朋友圈》](https://my.feishu.cn/docx/ZWM8dlTsgotKJHxy1k6cqRiynie)

```text
IMA 原文
→ Obsidian 标准素材卡
→ 15 个可追溯语料块
→ 5 个候选选题
→ 人工选择
→ 公众号草稿＋朋友圈文案
```

## 六、第一次建知识库，小白可以怎么做

![图 6｜第一次创建 Obsidian Vault 的入口](https://feishu.cn/file/VCOdbJz2vojdPnxv7H1coz4dn2f)

如果让我重新从零开始，我不会先研究标签体系，也不会先装一堆插件。

**第一步，只选一个真实问题。**比如：“我想把每天看到的公众号文章保存下来，并在写朋友圈时找得到。”问题越具体，第一套目录越简单。

**第二步，只选第一批会马上用的内容。**不要一次导入几千篇历史收藏。先放十篇以内，最好是未来两周准备写、讲或交付的材料。

**第三步，只建四个目录：**Inbox、Notes、Archive、Outputs。主题标签等内容多起来再加。

**第四步，手动跑一条。**收一篇、读回一篇、拆一条、写一个成品。这个过程能暴露权限、路径、格式和账号问题，也能让你知道自己到底需要哪个工具。

**第五步，删掉暂时不需要的安装项。**刚开始可以不装 Obsidian MCP、不装 Hermes、不做定时任务，也不用同时打通三个知识库。手机先用 IMA，电脑加工用 Obsidian，需要分享时再用飞书，已经足够。

新手最容易卡住的地方，往往不是写代码，而是没有说清楚“从哪里来、到哪里去、成功是什么”。

给 Codex 下任务时，把源头、目标库、目标路径和验收方式说清，问题会少很多。

## 七、内容多起来以后，怎样升级成大型知识库

| **机制** | **解决什么问题** | **最低验收标准** |
|-|-|-|
| 去重 | 避免同一内容反复入库 | 重复执行一次，不新增副本 |
| 日志 | 知道每次同步做了什么 | 能看到来源、目标、时间、状态和错误 |
| 失败重试 | 处理临时网络或接口异常 | 有限次重试，连续失败时提醒人工 |
| 定时检测 | 减少重复手工检查 | 先手动跑通，再从低频开始 |
| 写后验收 | 避免只看接口成功 | 目标端能搜索、打开并读到完整内容 |

当 Inbox 长期积压、同类内容经常重复、一个目录里已经难以找到东西，或者同一份内容开始服务不同项目时，就该升级了。

我会从三个方向加结构。

**第一是分层。**原始素材、精炼笔记和最终成品必须分开。原文保留出处，Notes 写自己的判断，Outputs 记录最终发布版本，三者不要互相覆盖。

**第二是加状态，而不是狂加主题标签。**除了 Inbox、Notes、Archive、Outputs，还可以增加“待核实”“待发布”“已发布”。状态回答的是“下一步做什么”，比几十个模糊标签更有用。

**第三是确定主仓。**哪一端保存原始来源，哪一端负责加工，哪一端负责交付，要提前定好。我的默认是：IMA 和网页剪藏负责进料，Obsidian 是加工主仓，飞书是协作和交付端。若某篇内容原本就在飞书完成，它也可以从飞书出发，但加工后的主版本仍要明确，目前明确终点就是Obsidian。

分库也不要只看文件数量。当不同内容的使用人群、权限范围或生命周期明显不同，比如个人素材、团队项目和对外付费交付需要不同成员访问时，再拆成独立知识库。

标签则适合处理跨目录、反复出现的主题；一个主题连续出现、确实需要横向检索时再加，不必第一天就设计一套庞大的标签树。

## 八、我实际踩过的几个坑

### 坑一：工具升级了，教程还停在旧版本

当时我觉得，只要一条旧命令曾经跑通过，就可以一直写在教程里。后来微信读取方案、飞书 CLI 的参数都升级了，知识库不同页面却还保留着旧说法，读者照着做自然会卡。

后来我把电脑端微信方案统一成 yichen-wechat-local-vault，并重新核对 `lark-cli` 的当前帮助。给新手的建议是：教程里的命令只代表当时版本，真正执行前先让 Agent 检查本机版本和官方说明。

### 坑二：没有先定主仓，内容在多个平台重复

一开始我觉得，多存一份总归更方便更踏实。等 IMA、Obsidian、飞书里都出现同名内容以后，反而不知道哪份最新的，也不敢改。

后来我规定 Obsidian 保存加工主版本，飞书保存协作或交付版本，IMA 更偏入口取料和AI对话；同步时携带来源和状态。给新手的建议是：**备份可以多份，主版本只能有一个**。

### 坑三：一开始就想把所有环节自动化

当时我想的是，最好每 30 分钟自动检查、自动清洗、自动分发。真正遇到错误时，却不知道问题出在取料、权限、去重还是写入。

后来我改成三级：先手动触发，再做增量同步，最后才定时运行。给新手的建议是：**自动化不是起点，它只是把已经稳定的手工流程放大**。

### 坑四：之前误以为安装 MCP 才能更好的读 Obsidian

之前我写过一个关于Codex安装Obisidian MCP的教程，写着直接读文件“不懂双链、标签和 frontmatter”。这并不准确，Codex 可以直接理解这些 Markdown 结构，MCP 只是把高频动作封装得更顺手。

后来我把 MCP 改成选装项。给新手的建议是：先用最短路径解决问题，遇到频繁检索和批量维护需求时再装。

### 坑五：忽略会员、权限和账号范围

接口和工具装好了，不代表账号就有资格调用。比如得到大脑官方 MCP 和 OpenAPI 当前明确要求会员账号；飞书也要检查应用权限、文档权限和知识库成员范围。

得到官方的 [MCP 使用指南](https://doc.biji.com/docs/FmYfw0yXsiXdTtkVzhLcuX8lnxd) 和 [开放平台](https://www.biji.com/openapi?tab=docs) 都写明了会员前提。给新手的建议是：安装前先列前置条件，尤其是会员、授权、账号和目标空间权限。

### 坑六：同名目录不等于同一个知识库

我还遇到过两个同名的 Obsidian 知识库分布在不同路径里：一个只看到部分目录，另一份才是完整内容。只看文件夹名字，很容易把 Agent 指到错误位置。

后来我先核对绝对路径和完整目录，再统一修改相关 Skill、Agent 和自动化配置，最后搜索旧路径是否还有残留。给新手的建议是：路径一旦变化，不能只搬文件，所有依赖这个路径的流程都要一起验收。

## 九、哪些适合自动化，哪些必须自己确认

**适合自动化的**，是规则清楚、可重复、出错后能回滚的动作：检查新内容、按固定路径写入、生成初步摘要、拆出候选语料块、维护索引、记录日志和发送失败提醒。

**必须保留人工确认的**，是需要判断或风险较高的动作：这条内容值不值得留，AI 的总结有没有歪，聊天记录是否应该被引用，哪一版可以发布，以及删除、覆盖、批量移动和对外发送。

我的经验是，**AI 很适合做“搬、拆、找、对、记”**，但**内容立场、隐私边界和最终发布，应该留在人手里**。

## 十、给第一次动手的圈友：今天就能做的最小清单

不用等工具全部准备好，直接拿一篇你手头就有的文章开始。

1. 选一个入口：不管手机还是电脑就都用 IMA。
2. 专门建一个 Obsidian Vault，只放 Inbox、Notes、Archive、Outputs 四个目录。
3. 把这一篇内容让Codex调取Ima skill 放进 Obsidian里的Inbox。
4. 让 Codex 拆出三条「候选语料块」，自己只保留最有用的一条。语料块提示词见
5. 把它改成一条朋友圈、一条短视频或公众号文章。
6. 再把完成的内容通过Codex回传给ima和飞书。（存档用可以不回传，要直接在ima或者飞书使用务必回传）

## 结尾

这套系统搭到最后，我越来越确定：**工具是起点，把工具的特征和业务需要结合起来，让内容流动起来**。

如果它只是被收藏，它还是原料；如果它变成了你的观点、作品、方案，甚至帮助你解决了一个具体问题，**它才真正成为你的知识**。

我现在做的，不仅仅是追求一套高效的内容系统，更是可以贯穿产品和变现的业务系统。

以产品和变现为终点，倒推设计内容系统。
